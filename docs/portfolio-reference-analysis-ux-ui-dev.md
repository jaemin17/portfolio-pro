# ux-ui.dev 作品集参考分析

记录日期：2026-11-05  
参考网站：[Sergei Kovtun — Product Designer](https://www.ux-ui.dev/)

## 阅读目的与范围

以应聘产品体验设计岗位为目的，研究这个网站如何组织项目、呈现能力、解释设计判断，再提炼值得借鉴的内容框架。本文暂不受现有作品集章节限制，也不是已经确定的改版方案。

已阅读首页的 5 个正式案例，并查看 Coherent 产品页，以及 Hero Lab 的 16 项实验介绍与实现说明。没有逐项运行 Hero Lab 的交互，也没有独立核实作者的履历和项目数据。

文中的项目数据、职责与实施情况来自作者自述；关于招聘信号、优点、不足和借鉴方向的内容是我们的分析。无法仅凭网站判断作者实际获得了多少面试或 offer。

## 核心判断

这个网站最值得借鉴的是：围绕同一个职业定位，让不同项目承担不同的能力证明任务。

在具体案例写法上，建议组合参考：

- **Email Marketing Platform**：整体结构与快速阅读。
- **Avanir Intranet**：证据如何推动方案变化。
- **1inch**：设计判断、收益与代价如何表达。

网站并不是严格的“7 个项目对应 7 项能力”。它包含 5 个正式案例和 2 个个人项目，设计系统、复杂流程、协作等能力反复出现。每个项目有主要重点，同时有其他能力支撑。

## 一、逐个项目分析

### 1. Email Marketing Platform：复杂产品架构与完整流程

[案例链接](https://www.ux-ui.dev/work/email-campaign-platform)

**内容顺序**

职责与协作 → 产品概览与变化 → 核心问题 → 用户角色 → 信息架构与任务流程 → 前后对比 → 模块设计 → 状态细节 → AI 与设计系统 → 反思。

**好的地方**

- 先给产品全貌，再逐层展开，读者较容易理解职责范围。
- 围绕营销活动生命周期解释模块之间的关系。
- 同一任务的前后对比，使改变容易理解。
- 区分保密重建示意与生产界面，部分改进也明确标为作者现在建议的修改。

**不足与阅读时需要区分的内容**

覆盖模块、AI、文档代理和系统建设，范围较大，主线容易被稀释。“改了什么”的展示强于“如何确认改得有效”的说明。示意界面中的数据不能当作设计带来的业务结果。

**值得参考**

先给全貌，再选择重点深入；前后对比围绕相同任务展开，并交代改变的意义。

### 2. Empower：设计系统如何服务团队

[案例链接](https://www.ux-ui.dev/work/empower)

**内容顺序**

职责 → 跨团队问题 → 个人责任 → 系统方案与成果摘要 → 建设方法 → 基础、组件、状态与响应式规范 → 交付协作 → 影响 → 反思。

**好的地方**

- 以重复建设、行为不一致、协作成本为起点。
- 将组件和规范与团队交付联系起来。
- 将采用机制、维护责任和治理视为系统的一部分。

**不足与阅读时需要区分的内容**

作者报告交付周期从数周缩短到数天，但测量范围与方法交代有限。若增加一次具体的组件争议、迁移或采用过程，能更充分证明治理怎样运作。

**值得参考**

展示规范时说明：解决了什么重复问题，怎样被团队使用，谁来维护，以及如何判断是否有效。

### 3. 1inch：复杂决策中的设计取舍

[案例链接](https://www.ux-ui.dev/work/1inch)

**内容顺序**

职责与背景 → 用户决策困难 → 总体方案 → 多产品设计展示 → 方法 → Fusion 专题深挖 → 结果 → 反思。

**好的地方**

- 具体说明信息层级与交易判断的关系。
- 基础界面隐藏部分高级参数时，也交代对高频用户的代价和快捷入口的补偿。
- 专业界面保留高密度，按任务组织信息，体现不同场景下的不同判断。
- 在广度展示之外，选择一个关键流程深入讲解。

**不足与阅读时需要区分的内容**

总览、方法和专题之间有重复。部分结果因保密只提供方向性描述，读者难以判断效果大小。平台交易规模是背景，不能归为个人设计成果。

**值得参考**

每个关键决策说明：服务谁、解决什么、为什么选它、接受了什么代价，以及怎样补偿。

### 4. GETTR：快速交付与跨团队一致性

[案例链接](https://www.ux-ui.dev/work/social-platform)

**内容顺序**

职责 → 高速增长背景 → 并行开发的问题 → 统一策略 → Web/App 展示 → 研究与流程设计 → 系统与协作 → 影响 → 反思。

**好的地方**

- 说明团队环境与时间压力，让读者理解工作的难度。
- 以多团队并行开发解释共享模式和系统的必要性。
- 将设计工作放在真实组织和交付环境中。

**不足与阅读时需要区分的内容**

证据偏宏观。流程与线框数量能交代范围，不能充分说明质量。更适合补充一次具体冲突、优先级判断或反馈驱动的迭代。平台用户增长也不能直接归因于个人设计贡献。

**值得参考**

讲清工作环境，并用具体事件解释自己的协作与判断如何产生作用。

### 5. Avanir Intranet：研究与限制如何推动方案变化

[案例链接](https://www.ux-ui.dev/work/avanir-intranet)

**内容顺序**

背景与职责 → 旧版问题 → 分析与调查 → 信息架构 → 两个首页方向 → 焦点小组反馈 → 品牌约束 → 方案收敛 → 上线与响应式 → 结果与反思。

**好的地方**

- 比较新闻优先与工具优先的方案，让选择有具体对象。
- 展示员工反馈与品牌代理方的不同要求。
- 解释反馈和限制如何改变最终设计，保留真实工作的分歧。
- 结果包含时间范围：作者报告上线首月门户用户增长 21%。

**不足与阅读时需要区分的内容**

20 比 17 的方案投票只表明轻微偏好，不能单独证明可用性更好。上线后的用户增长也可能受推广等因素影响，不能完全归因于设计。

**值得参考**

把发现、备选方案、反馈、修改和最终决定连接起来。这是五个案例中，最值得借鉴的方案演变叙事。

### 6. Coherent：独立产品与设计实现

[产品链接](https://www.getcoherent.design/)

**内容顺序**

核心价值 → 使用演示 → 问题 → 产品机制 → 操作示例与验证 → 开始使用 → 开源与常见问题。

**好的地方**

提供可继续查看的工具、代码和文档，让商业案例之外的实现能力有直接载体。产品围绕设计系统、复用和维护，延续作者的专业定位。

**不足与阅读时需要区分的内容**

产品存在不等于用户价值已经充分验证。产品介绍页与设计案例的证明任务不同，不能仅凭功能陈述判断采用和效果。

**值得参考**

独立项目可以用真实体验、持续更新和实现细节证明能力，不必全部写成长篇流程案例。

### 7. Hero Lab：创意、动效与技术探索

[实验链接](https://www.ux-ui.dev/lab)

**形式**

16 项实验配有简短的制作说明，涵盖滚动变化、界面分层、玻璃效果、粒子、3D 建筑与视频等。

**好的地方**

为正式案例补充视觉探索、动效和技术兴趣。独立放置使主案例保持聚焦，又增加个性和可体验内容。

**不足与阅读时需要区分的内容**

实验能证明探索与实现兴趣，不能直接证明复杂业务问题的解决能力。本次没有逐项运行验证交互效果。

**值得参考**

探索作品承担补充作用，重点案例承担产品设计能力的主要证明。

## 二、网站整体为什么有说服力

### 1. 定位集中

首页以“让复杂产品更容易使用”建立定位，案例围绕复杂流程、系统和协作持续提供支撑。简历、推荐语和联系方式进一步形成求职阅读路径。

### 2. 项目之间有分工

| 项目 | 分析归纳的主要证明任务 |
| --- | --- |
| Email Marketing Platform | 复杂架构与完整流程 |
| Empower | 系统建设与团队采用 |
| 1inch | 高风险场景中的判断与取舍 |
| GETTR | 快速交付与跨团队一致性 |
| Avanir | 研究、反馈与方案演变 |
| Coherent | 独立构建与设计实现 |
| Hero Lab | 创意、动效与技术探索 |

这些是重点，不是互斥分类。一个项目依然需要其他能力支撑。

### 3. 兼顾快速浏览与深入阅读

多数案例开头交代产品、职责、问题和总体方案，后面再展开设计证据。读者不用读完所有过程才知道作者做了什么。

### 4. 设计物附带用途与原因

界面、流程、规范通常说明它们服务的任务，成为论证的一部分。展示数量本身不承担全部证明任务。

### 5. 具体限制与取舍增强可信感

品牌约束、专业用户需求、团队维护成本、保密与未上线建议，使读者能理解方案的实际条件。

## 三、值得保留的批判性判断

- 叙事可信与证据充分是不同维度。
- 有些案例的效果陈述较概括，缺少样本、测量方法和前后基线。
- 项目规模、平台用户数与交易量应和个人成果区分。
- 数量多不等于设计质量高。
- 多个案例反复强调复杂性和设计系统，也会带来重复感。
- 应区分真实上线、保密重建、事后建议，以及新补做的验证。

## 四、我们可以借鉴的内容框架

### 固定开头、灵活主体、明确结尾

| 部分 | 必须回答的问题 |
| --- | --- |
| 项目摘要 | 什么产品？服务谁？我负责什么？主要改变是什么？ |
| 背景与核心问题 | 为什么需要设计介入？问题怎样影响用户或业务？ |
| 判断依据 | 怎样发现问题？哪些证据改变了理解？ |
| 总体策略 | 优先解决什么？为什么这样组织方案？ |
| 两三个关键决策 | 有哪些选择？依据是什么？接受了什么代价？ |
| 完整体验与落地 | 流程、状态、技术限制和协作如何处理？ |
| 结果与复盘 | 已确认什么？怎样确认？仍有什么局限？ |

主体随项目变化：研究推动明显时展开方案演变；交互判断突出时深入关键流程；系统建设为主时解释采用和维护。

用户研究、竞品分析、流程图、原型与设计系统可以作为证据。是否独立成章，取决于它们对理解设计决定的重要程度。

推荐组合：采用 Email Platform 的阅读顺序，用 Avanir 的证据链和 1inch 的取舍表达充实主体，并补强结果验证。

## 五、每个项目讲一个重点能力：讨论中的暂定方向

结合“App 产品体验设计师”的职业方向，初步分工如下。这些是待证据检验的假设，尚未确定为项目目录。

| 项目 | 建议主重点 | 希望招聘方记住什么 |
| --- | --- | --- |
| Selfly | App 产品体验与从 0 到 1 的判断 | 围绕真实需求持续作出产品取舍并落地 |
| 模型编辑器 | 复杂交互的易用性 | 将专业操作整理成可理解、可控制的体验 |
| XR 课件 | 信息架构与任务流程 | 将模型、内容与教学步骤组织成完整工作流 |
| VR 教育与实训 | 空间场景中的交互与引导 | 根据使用环境设计信息、反馈和指引 |
| 图标等视觉项目 | 视觉提炼与一致性 | 有具体的视觉判断和细节完成度 |
| 个人工具探索 | 主动发现问题与快速验证 | 将日常观察转化为可体验的产品 |

作品数量取决于证据质量，不需要对齐参考网站的七个。并非每个作品都需要长案例。初步建议让 Selfly 承担 App 方向的主要定位，模型编辑器证明复杂问题处理能力，其他作品补充广度。

## 六、下一步讨论事项

1. 确定整份作品集优先证明的能力。
2. 为每个重点项目选择一个主能力，同时列出支撑能力。
3. 建立“项目—主能力—具体证据”表，区分已有事实、个人判断和待验证假设。
4. 据此决定主案例、辅助案例与探索作品，再确定各项目的具体目录。
